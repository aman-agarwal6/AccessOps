# Evidence and release verification

Evidence has three origins: browser simulation (no external effect), local
verification (actual test execution on a workstation), and CI verification
(actual clean workflow execution). A report describes its test scope. It is not
automatically evidence that Keycloak was contacted or a model was evaluated.

`tools/evidence.py` converts an actual JUnit report into an allowlisted archive,
retaining passed, failed and skipped cases. It records revision, dirty state,
input hashes, run/attempt and file hashes. It excludes raw logs, environment,
tokens, certificates and arbitrary files. Changes during collection invalidate
the export. An optional SBOM must be CycloneDX 1.6 JSON.

```powershell
python tools/evidence.py begin --output output/source-inputs.json
# Run the documented checks and write their actual JUnit report.
python tools/evidence.py freeze --report output/backend.xml --inputs output/source-inputs.json --output output/local-receipt
python tools/evidence.py verify output/local-receipt/accessops-evidence-COMMIT.tar.gz
python -m unittest discover -s tools -p 'test_*.py'
```

Hash verification detects modification relative to the manifest. It does not
establish a trusted origin: an attacker can replace the manifest too. A released
archive is signed by the isolated manual main-branch workflow. The provenance
and SBOM use the exact archive digest. Detached Sigstore bundles stay outside
the frozen archive; no signature is inserted into its own signed bytes.

The public console index is generated by `python tools/publish_recordings.py`
from fixed, sanitized JSON/JUnit report paths. It retains failures, dates and
limitations; source file hashes do not invent a Git revision or signature.

The release SBOM catalogs the locked Python runtime and npm dependency inventory.
It does not claim to catalog every operating-system package inside base images or
the separately installed optional model weights. Image digests are recorded in
the runtime lock; their layer scans are a separate verification scope.

Fetch trust roots independently with GitHub CLI on a trusted online machine.
Pin the expected repository, workflow and source ref from the release you chose,
not from instructions inside an untrusted archive. Inspect the verified JSON
predicate's revision against your expected commit.

```text
gh attestation trusted-root > trusted_root.jsonl
gh attestation verify ARCHIVE -R aman-agarwal6/AccessOps --signer-workflow aman-agarwal6/AccessOps/.github/workflows/release-evidence.yml --source-ref refs/heads/main --source-digest EXPECTED_COMMIT --deny-self-hosted-runners --bundle provenance.sigstore.json --custom-trusted-root trusted_root.jsonl --format json
python tools/evidence.py verify ARCHIVE
```

The [official offline verification guide](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/verify-attestations-offline)
explains root rotation and detached bundles. Provenance, SBOM, vulnerability
scan, license report and application-test results answer different questions.
There is no compliance badge or claimed SLSA level in this project.
